# Experience-based Examine: repository audit and proposed design

Status: design proposal, not an implemented feature. Audited October 15, 2026 (America/Chicago), against local HEAD `4fc2c0bbd55193bc68958518b72beefe856370be`, immediately following [the field-ledger commit](https://github.com/stevenrichter16/caves_of_ooo/commit/f14ec7e51a937415b89414ce2525ed5b3286957b). The checkout also contains existing uncommitted work, including save, inventory, throwing, and Examine changes; those were read but not changed. Findings below distinguish source inspection from proposed behavior. No runtime tests were executed for this design audit.

## Recommendation

Add a player-owned, explicitly serialized observation ledger, fed by small adapters at committed gameplay boundaries. Each adapter captures what the player could perceive at that moment. Authored rules turn that evidence into narrow claims. A shared disclosure policy projects those claims into every Examine presentation.

Start with witnessed melee behavior: seeing a viper strike with its fangs teaches that behavior, even if it misses. It does not teach its damage dice, penetration bonus, venom probability, or the absence of other attacks. Preserve existing atmospheric descriptions and immediate public danger cues.

The repository already has combat outcomes, causal strike IDs, local witnessing, historical reports, and save infrastructure. The missing piece is a common bridge from player-perceived evidence to durable, scoped facts and consistent disclosure. A general event-sourcing platform, new save container, global bestiary level, or rewrite of NPC knowledge is unnecessary.

## Proposed data and boundaries

The pipeline is:

`committed action -> event-time perception -> copied evidence -> fact rules -> saved player ledger -> disclosure projection -> AnnouncementDocument`

### 1. Observation receipts, not simulation dumps

Introduce a small simulation-facing `ObservationService` and an immutable value receipt. Begin with a `MeleeObservation` adapter inside `PerformSingleAttack`; extend through separate adapters for ranged attacks, spells, item use, harvest, material reactions and reading later. Do not subscribe to every event globally or scan every entity's components each turn.

An internal producer may know the selected weapon and true outcome. Its public evidence payload must contain only allowed perceptual tokens, for example `fang_strike`, `missed`, or `visible_wound`. Never copy damage dice, hidden effect specifications, NPC goals, unused abilities, internal resistance values, or complete component snapshots into a record that UI can read.

Capture participants, occupied contact cells, observed appearance, and eligibility before death/removal. Capture outcome visibility at the corresponding contact/change boundary, before cleanup. Do not let seeing the attacker earlier authorize an outcome behind a newly closed door or cloud. An attack interrupted before execution provides no completed-attack fact; a visible windup can be a separate tell if that producer is added. A valid swing with a miss still provides behavioral evidence.

Use existing `ActionId`, `StrikeId`, and parent/root ancestry. One strike produces one finalized receipt. Deduplicate receipt delivery per observer/session and strike/occurrence ID; count distinct actions per `(fact key, subject/family scope, ActionId)` so an off-hand chain does not masquerade as several independent encounters. A global action-ID seen-set would incorrectly suppress a counterattacker or a different fact from the same action. Correlated effects use the strike ID plus a distinct effect occurrence ID. Neither turn number alone nor message text is a reliable deduplication key.

Publish synchronously before the enclosing action becomes saveable. Finalize valid early returns too: miss, full parry, armor stop, zero damage, and attacker death from retaliation. Do not mint a success receipt from an exception or rejected action. Capture facts at their committed boundaries so later follow-up attacks cannot rewrite them.

### 2. Event-time player perception

Extract a shared, simulation-callable visibility calculation from the existing player FOV geometry. Return an immutable snapshot/mask; separate that query from the current `Compute` method's mutation of `IsVisible` and `Explored`. Presentation can consume the same result. Preserve the configured player FOV radius and current wall/cloud rules; do not substitute NPC `HasLineOfSight` and silently change what the player can see.

For the first slice, recomputing at an eligible attack boundary is an acceptable correctness-first implementation. Cache only against explicit observer-position, zone-occlusion and perception revisions once measurement justifies it. Observation must work with rendering, audio and diagnostics disabled.

Check the actual player, current zone, current occupied cells, physical ownership and `RenderPart.Visible`. For large creatures use the visible occupied surface, not just the anchor. Seeing only the victim grants no attacker identity. Seeing the attacker but not contact permits its visible motion, not the hidden victim's condition. Being hit by an unseen source permits a self-experience record without a species attribution. Seeing a glow does not identify its hidden owner.

The present source does not establish a general blindness/darkvision/hearing model. Do not invent a darkness restriction from `LightMap`. Keep sensory eligibility behind this interface so such rules can be added deliberately. Auditory evidence should later retain an unknown source unless the player can actually associate it with an actor.

### 3. Player-owned evidence and fact state

Proposed `ObservationJournalPart : Part, ISaveSerializable` owns records and a fact index. Use `FactBag` for integer projections/counters if useful; keep the existing NPC `KnowledgePart` wire format and tier semantics intact. A second mandatory `KnowledgePart` cache would create two sources of truth and is unnecessary.

Suggested value fields:

| Record | Fields |
| --- | --- |
| Evidence | schema version; evidence/strike/action IDs; tick; world/zone context; subject GUID; optional recognized family ID; perceived appearance/label; observation token; modality (`Seen`, `Experienced`, `Heard`, `Read`, `Told`); permitted outcome token; causal IDs where available |
| Fact definition | stable semantic key; claim text templates; required evidence types/modality; scope; explicit generalization policy; inference policy; disclosure precision |
| Fact state | key and scope; status (`Observed`, `Suspected`, `Supported`, `Contradicted` as applicable); distinct action count; first/last evidence ticks; supporting evidence summaries; rule version |

These names are proposed APIs, not existing classes or facts. Example key: `creature.viper.behavior.fang_strike`.

Keep facts proposition-specific. “I saw it strike with fangs” can be established after one clear observation. “Its bite carries venom” is a different proposition. Firsthand, hearsay, and inference are provenance categories, not sequential confidence tiers. Direct experience can still support an uncertain mechanism. Conflicting evidence can weaken a hypothesis without erasing the historical event.

Scope individual wounds, equipment, temper and temporary effects to an individual. Generalize authored species behavior only to a recognizable, explicitly mapped family, with wording such as “You have seen vipers strike with their fangs.” A sword carried by one viper, a mutation, or an exceptional attack must not become universal species knowledge. Material claims require evidence about a recognized material; never infer composition from the object's name.

`Entity.ID` is saved but is assigned by a per-factory integer counter in `EntityFactory`; no load-time allocator rebase was found. Do not assume it is globally collision-free. The small safe addition is a lazily stamped GUID observation identity in an entity property, already supported by saves. Clear/regenerate it on clone/split: `Entity.CloneForStack` currently copies every property even though it assigns a new `Entity.ID`. Define merge behavior before enabling object-instance evidence for stacks. Never stamp identity as a side effect of rendering Examine. Use stable authored family IDs for allowed generalization; do not display hidden blueprint names as discovered identities.

Persist value data, not references to every witnessed Entity: the save graph follows Entity references and could otherwise retain dead creatures and their inventories. Keep bounded representative evidence per fact plus aggregate counts and first/last dates. Retain unlocked facts; pruning evidence detail must not forget discoveries. For the synchronous MVP, receipts are never replayed on load and deduplication covers the complete active action. A future replayable queue requires durable replay checkpoints; a finite recent-ID cache alone cannot guarantee arbitrary replay idempotence.

### 4. One disclosure projection for Examine

Add a pure `ExamineKnowledgePolicy`/projection taking an explicit viewer, the authorized subject context, and the viewer's ledger. It returns permitted description sections and facts. `BuildWorld`/`BuildInventory` keep their existing access checks. A missing viewer or ledger grants only explicitly public information, never full knowledge.

Use three kinds of content:

- **Visible now:** appearance, visible wounds, exposed flame, current public windup/recovery, readable signs, ordinary action affordances. This layer still uses current state, but only via approved sensory descriptions. Keep `CombatIntentReadout` warnings useful immediately.
- **Field notes:** durable historical claims, their source and uncertainty. They remain about what happened then. A remembered poisoning does not mean this individual is currently poisoned; a dead specimen's behavior can remain known.
- **Understood mechanics:** only explicitly earned precision from appropriate study, testing, or established player knowledge. Repeating a bite observation never automatically unlocks dice, exact proc chance, resistance, immunity, maximum damage, or a universal negative such as “never dismembers.”

Keep atmospheric `ExaminablePart.Text`, but audit authored text for concealed mechanical/identity claims; prose is also a disclosure route. Split those claims into gated definitions where needed. Unknown fields should normally be omitted, not enumerated as a checklist revealing how many secret attacks exist. Preserve directly visible form/portraits and ordinary labels; a future identification system must route titles and portraits through perceived appearance too.

Do not pass full `EffectDescriber` output for another creature's visible condition: it currently includes timers, dice and saves. Provide qualitative observations such as “Blood darkens its flank.” Likewise separate visible material/condition from exact composition, structure HP and repair recipes. Ownership alone does not identify a mysterious item's payload. Familiar equipment numbers may be designated baseline player knowledge by an explicit authored policy; they must not become an implicit “all components known” fallback.

Route `ExaminablePart`, `InputHandler.OpenWorldExamineReader`, inventory Examine, decision details, and their log/accessibility fallbacks through the same projection. Construct legacy text from the authorized document (`ToPlainText`) instead of independently calling unrestricted providers. Audit equipment comparison and related item panels for the same hidden facts. Keep raw mechanical formatters available internally where genuinely needed, but no automatic public fallback on an unknown fact.

Opening, scrolling or reopening Examine is read-only: no RNG, discovery count, identification, remote-zone generation or evidence refresh. If deliberate inspection should later teach something, implement a distinct committed inspection action.

## Worked example: a witnessed viper attack

The shipped `Viper` blueprint selects `ViperBite`; [NaturalWeaponFactory](../../Assets/Scripts/Gameplay/Anatomy/NaturalWeaponFactory.cs) constructs a fangs weapon with an on-hit venom payload. Those are simulation facts, not starting player knowledge.

1. The player has no attack evidence. Examine shows the creature's available appearance/flavor and visible condition. It does not inspect the bite's effect configuration to populate field notes.
2. The viper actually attempts a fang strike. `PerformSingleAttack` already selected the weapon and assigned a strike ID. The observation adapter captures the player's event-time view and approved `fang_strike` token.
3. The attack misses. Resolution commits one `Seen` receipt. A rule establishes only the behavior fact. Examine now says, for example, **“You saw it snap forward with its fangs.”** A miss cannot reveal venom or prove weakness. An unseen duplicate encounter teaches nothing.
4. A later visible strike hits. Record its visible contact; numerical damage, if part of the player's self-feedback, remains one realized outcome, not a weapon formula. Repeated eligible actions can change the wording to **“You have seen this quick fang strike several times.”** They do not unlock unrelated facts.
5. In a later extension, a successful, perceptible effect linked to that strike supplies separate evidence. A player who feels illness after the bite may record **“Sickness followed its bite; venom is a possibility.”** An independently observed symptom does not prove causation. Seeing only a victim stagger does not identify the exact `PoisonedEffect`. Existing source/strike ancestry helps correlate events internally; authored rules still limit what the player can conclude. A rejected effect, unobservable effect, preexisting illness, or delayed unrelated damage cannot grant this claim.
6. Save after the action completes, even before opening Examine. Reload into fresh objects. The same fang-strike note is present. Venom remains unknown if step 5 never happened. Encountering another recognizable viper can show the historical family note, while its current wounds and equipment remain independent.

The first release ends at steps 1–4 and 6. Step 5 demonstrates the extension boundary rather than making status attribution a prerequisite for useful attack discovery.

## Smallest useful implementation and integration order

1. **Add the journal and identity helper.** Explicit, versioned `Save`/`Load`; bounded validated value records; deduplication; stable family mapping for the pilot. Attach on new-player bootstrap and ensure an empty ledger/rebind service after `GameBootstrap.ApplyLoadedGame` assigns the loaded player. Loaded Parts are reconstructed without normal `Initialize`, so relying on that method alone is insufficient.
2. **Extract event-time perception.** Share FOV semantics with rendering and expose a query without exploration side effects. Cover stale visibility and large-body contacts before enabling writes.
3. **Instrument actual melee attempts.** Integrate at `CombatSystem.PerformSingleAttack` and committed contact boundaries, using existing provenance/results. Start with authored natural-weapon behavior such as viper fangs; unknown attack forms stay generic. No use of audio, diagnostics, message parsing or outer action animations as evidence authority.
4. **Project one new Field notes section and gate existing disclosure.** Centralize viewer-aware filtering across structured, legacy and inventory paths. An attack-only producer can ship while unsupported discovery-dependent fields remain hidden; adding the section while leaving secret mechanics elsewhere would not satisfy the goal.
5. **Prove native persistence and non-disclosure.** Complete the tests below. Then add adapters individually for committed empty-ray swings/windups, ranged/mutation/spell attacks, item experimentation, successful effects and material reactions. `PerformSingleAttack` alone does not cover every attack: committed empty rays never call it, and ranged/spell paths use their own resolution.

No bestiary screen, exhaustive event archive, general probabilistic inference engine, new global save section, or NPC knowledge migration is needed. Fixing brewing's separate save gap is worthwhile but not a dependency of the melee slice.

## Save compatibility and lifecycle

The current outer save format is version 8 and checks exact version equality. Adding an optional serialized Part can preserve existing version-8 saves: absent journal means empty knowledge, established by bootstrap. Do not backfill discoveries from current components, visited zones, old logs, NPC knowledge or already loaded creatures. This does not promise support for older outer formats.

Give the new Part an internal schema version and length-delimited records with count/string limits. Load into temporary validated state before applying it. Unknown fact IDs remain non-disclosing; retain opaque records only when they can safely be skipped and preserved. Incompatible Part payloads must reject safely rather than partially grant knowledge. The existing outer codec cannot generally skip arbitrary unknown Part payloads, so backward compatibility with old saves does not imply old executables can read new saves.

Update knowledge on the simulation thread before save capture; the existing strike/action guards define that boundary. The background writer receives detached serialized bytes. Rehydration, zone reconstruction, renderer rebuild and UI queue restoration must not replay observations. However, `ApplyLoadedGame` can call `ProcessUntilPlayerTurn`: bind the observation service before that call, because genuinely new attacks during resumed simulation must record normally. Restore current conditions from the world and historical facts from the ledger independently.

## Required tests and acceptance criteria

These are proposed tests, not passing results. Add focused core tests, full native session persistence tests, and Unity UI integration coverage; a collection-copy helper test is insufficient.

| Test | Required assertion |
| --- | --- |
| Visible actual strike | Real `PerformSingleAttack` produces one behavior note for a qualified witness; miss, parry, armor stop and hit are distinct outcomes. Rejected action/cancelled windup produces no executed-attack fact. |
| Unknown mechanics | After one and many strikes, poison configuration, dice, hit/penetration bonuses, resistance, unperformed attacks, and dismemberment guarantees remain absent. Run the native Unity suites for the complete implementation before calling the feature verified. Separately add a real native `BrewKnowledgePart` persistence regression to confirm the audit finding.
