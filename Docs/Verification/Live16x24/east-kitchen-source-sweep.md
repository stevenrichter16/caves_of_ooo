1. **Projection already stays flat everywhere.** This packet extends regional native-sprite permission from the current four graphs to two exact current Spread graphs; it must not alter global 16×24 projection, default launch, or 3D restoration. `FlatPixelGreyboxCatalog.IsAdmitted(Zone)` currently switches only Y and hardcodes POI X=11 (lines161–176). Preserve canonical graph/map/Spread checks from `SpreadPresentationScope.IsActive` (`Gameplay/World/Generation/SpreadPresentationScope.cs:19–53`). No living-site, seed, exploration-version, resident-name or job-state admission gate: older/depleted/destroyed saved sites still need consistent presentation.
2. **The approved Cook is already finished native artwork.** Reuse its exact bytes; do not regenerate or raster-trace it. Active source is `ArtSource/CookDownloads/cook.png` and editable `cook.piskel`, not the earlier `ArtSource/Cook16x24` alternative. Source and `Assets/Art/Cook16x24/cook-16x24.png` are byte-identical SHA256 `d534b0e3cab143d8a1523829fc4bd101b76d776d307a152fd18cfe9c5681dbdd`:16×24,165 opaque pixels,8 colors,binary alpha,one Piskel frame. Source image inspected. Existing import is Sprite Single,16PPU,bottom-center,FullRect,Point,Clamp,uncompressed default,no mip/NPOT resize. An old13×24 sprite-sheet subsection is not the active Single sprite. It is outside Resources. A separate byte-identical texture resource can feed a centered16×24 tile while preserving the old prefab/GUID/bottom-pivot asset. Do not crop the canvas, force an empty bottom row, or invent directional/walk frames.
3. **Forge and Oven have no persistent “working / ready” heat state.** `ForgePart` is an adjacency/service marker and component-picker verb surface (`Gameplay/Weaponcraft/ForgePart.cs:12–18,35–85`). `TinkersForge` is non-solid Furniture/Weaponcraft, not a blocker (Objects.json:5322). Ordinary Oven scenery only receives `CampfirePart {AllowRest=false,FiniteCooking=false}` on the generated kitchen owner (`SpreadExplorationResidents.cs:115–121`). Do not reuse finite campfire hot/cooled/flame frames or require Fuel/Thermal to make this actual station visible.
4. **Kitchen job state is richer than its public State string.** Private `Bound`, `ValidJob`, `InputsCurrent`, `OutputStored` enforce identities, contents and custody (`KitchenBatchPart.cs:61–121,193–218`). `Reconcile` / `ReconcileZone` explicitly mutate gameplay and must never be invoked by rendering (233–245). `OwnsCommissionedMeal` is a historical transfer receipt intentionally valid after pickup, not a current visible-ready predicate (220–229). Keep initial tray artwork neutral rather than imply a meal/recipe merely from nonempty Contents or State="Ready".
5. **Extend local art, not the exact opening ground/boundary kits.** G2 pond/path/soil and connected glade masonry each intentionally require `ReferenceGladePlan.IsActive`. Keep those gates. East's normal StoneWall can already use the dedicated full-cell masonry in the cellar atlas after native admission. Do not give east Wall/glade-unknown owners a fabricated glade VisualID. Existing ordinary vegetation, Stoneburr and loose-goods selectors can provide useful coverage, while unsupported CharterFlower/steam/pipe/mill/creature owners retain their actual glyphs until authored.

## State and repaint evidence / remaining trap

- Repair command commits `Repaired` and marks the actual owner's cell dirty (`RepairablePart.cs:148–160`): prove real repair→submitted pan tile change without movement/manual dirty.
- Existing CropPart/time/harvest machinery drives stages/removal and native repaint; use actual growth/harvest tests, including dropped product over soil. Prepared ground belongs to the separate terrain, not crop.
- Kitchen start/ready/cancel/collected call `Changed`, which marks pan,escrow,pickup dirty (`KitchenBatchPart.cs:360–364`). InputHandler calls `ReconcileZone` after the paid turn (`InputHandler.cs:1243`), after arrival (`1143`); bootstrap also reconciles on launch/load. Rendering must only observe.
- `ContainerPart.AddItem/RemoveItem` mutate contents/custody with **no presentation dirty event** (`Gameplay/Items/ContainerPart.cs:35–98`); `TakeFromContainerCommand` transfers transactionally but adds no general container redraw. Therefore a future ready/full/empty cue needs a real transfer→submitted-frame test, not repeated direct catalog queries. Don't add generic callbacks/watchers for neutral trays now.
- Future working/ready art would need a pure no-allocation snapshot of existing authority, not duplicated partial string checks: Bound identities/anchors, valid working job + exact escrow receipt; or actual one-unit owned FieldMeal in exact pickup. Some current private helpers allocate (`HashSet`, LINQ/new arrays), so simply exposing and polling them is not a zero-allocation solution. Reconcile, CanStart (builds input list), Describe and historical OwnsCommissionedMeal are unsuitable render queries.
