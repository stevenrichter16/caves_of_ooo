# Item composition: local Qud comparison after the 35-item pass

Status: read-only source investigation, 2026-10-08. No gameplay changes in this report. Compared the complete local reference tree at `/Users/steven/qud-decompiled-project` with current CoO after the 35-item implementation (`f239fb81b`). This is a bounded architecture/content comparison, not a claim about every behavior in either game or a live Qud playtest.

## Recommendation order

1. Give existing creature coatings deliberate, costly removal choices.
2. Introduce one reusable applicator that changes how existing liquids can be delivered.
3. Add a small set of conditional meal preparations, retaining the one-meal limit.
4. Treat liquid mixtures as a later, content-gated investment, not the next prerequisite.

The useful reference lesson is that an object's properties continue to matter across verbs and targets. Qud declares conductivity, combustibility, absorbency, flow, evaporation, staining and cleansing together, with separate contact/drinking hazards and wet/frozen surface behavior ([BaseLiquid.cs:34](/Users/steven/qud-decompiled-project/XRL.Liquids/BaseLiquid.cs:34), [BaseLiquid.cs:74](/Users/steven/qud-decompiled-project/XRL.Liquids/BaseLiquid.cs:74)). CoO already implements much of that physical vocabulary ([LiquidDefinition.cs:37](/Users/steven/caves-of-ooo/Assets/Scripts/Gameplay/Materials/LiquidDefinition.cs:37)). The next gains should connect existing rules into more complete player choices rather than introduce another large catalogue of unrelated activations.

## 1. Remove a coating through an intentional action

**Reference choice.** Qud asks both whether a target needs cleaning and whether the actor has an eligible cleaning source before offering the verb. It selects a source and charges an action after a successful cleanup ([Physics.cs:2720](/Users/steven/qud-decompiled-project/XRL.World.Parts/Physics.cs:2720), [Physics.cs:2741](/Users/steven/qud-decompiled-project/XRL.World.Parts/Physics.cs:2741)). Cleaning eligibility depends on liquid properties and available volume, rather than a single special named flask ([LiquidVolume.cs:5475](/Users/steven/qud-decompiled-project/XRL.World.Parts/LiquidVolume.cs:5475), [LiquidVolume.cs:5520](/Users/steven/qud-decompiled-project/XRL.World.Parts/LiquidVolume.cs:5520)). A liquid-covered effect itself participates in cleaning and conductivity events ([LiquidCovered.cs:372](/Users/steven/qud-decompiled-project/XRL.World.Effects/LiquidCovered.cs:372)).

**Actual CoO boundary.** Drenching extinguishes and adds Wet; it does not explicitly subtract body-coating quantity ([EmergencyDousingActions.cs:88](/Users/steven/caves-of-ooo/Assets/Scripts/Gameplay/Items/EmergencyDousingActions.cs:88)). Prismreed pith removes a thin **ground** coating ([MaterialFieldActions.cs:149](/Users/steven/caves-of-ooo/Assets/Scripts/Gameplay/Items/MaterialFieldActions.cs:149)). Body coatings dry down, and a larger incoming coating can replace the dominant liquid while adding both amounts ([LiquidCoveredEffect.cs:178](/Users/steven/caves-of-ooo/Assets/Scripts/Gameplay/Materials/LiquidCoveredEffect.cs:178), [LiquidCoveredEffect.cs:204](/Users/steven/caves-of-ooo/Assets/Scripts/Gameplay/Materials/LiquidCoveredEffect.cs:204)). Therefore “oil can never be displaced” would be false; the missing affordance is predictable, paid **removal** rather than dominance replacement. Staining is separately and explicitly deferred ([LiquidDefinition.cs:64](/Users/steven/caves-of-ooo/Assets/Scripts/Gameplay/Materials/LiquidDefinition.cs:64)); implementing cosmetic stains is not necessary for this recommendation.

**Proposed player situation.** A companion is pitch-covered beside an approaching fire user. Spend scarce absorbent pith to wipe away a bounded amount without wetting them, or use clean water for suitable washable residue and accept Wet's electrical liability. The alternative is retreating until the coating dries. Describe the exact eligible residue and amount; water must not magically dissolve oil, neutralize acid or cure internal poison.

**Bounded implementation.** Start with pith on the already authored oil/pitch/honey coatings, and a separately vetted washability table for water. Pith already has a real crop yield ([Objects.json:51003](/Users/steven/caves-of-ooo/Assets/Resources/Content/Blueprints/Objects.json:51003)). One item/action removes a capped quantity; large coatings need multiple actions. Use normal effect removal when exhausted so modifiers and lights reverse correctly. Preserve unrelated Wet, poison and burning. No generic stain simulation or equipment-contamination migration in this first delivery.

**Cost and verification.** The player sacrifices a useful ground-wicking supply, a turn and proximity; cleanup must not offer free status cures. Pair body/ground targets, eligible/ineligible liquids, partial/full removal, effect veto, exact payment and save restoration. This is the smallest next slice with an immediately understandable combat decision.

## 2. Make one discovered tool change liquid delivery

**Reference choice.** Qud's sprayer is a small delivery part layered over an ordinary LiquidVolume. It checks broken/rusted/empty state, selects an inventory/equipment target and applies the actual stored liquid as a coating ([Spraybottle.cs:21](/Users/steven/qud-decompiled-project/XRL.World.Parts/Spraybottle.cs:21)). This particular reference is **not evidence of a ranged enemy spray**. The broader pour path independently calls liquid-specific dousing behavior and contact processing ([LiquidVolume.cs:6282](/Users/steven/qud-decompiled-project/XRL.World.Parts/LiquidVolume.cs:6282)). The transferable idea is separating delivery hardware from the contents' consequences.

**Actual CoO boundary.** A liquid vessel already stores identity, quantity and capacity ([LiquidVesselPart.cs:3](/Users/steven/caves-of-ooo/Assets/Scripts/Gameplay/Items/LiquidVesselPart.cs:3)). Pouring is limited to an adjacent passable cell ([LiquidVesselService.cs:245](/Users/steven/caves-of-ooo/Assets/Scripts/Gameplay/Items/LiquidVesselService.cs:245)). The recent material entry points are intentionally authored by blueprint ([MaterialFieldActions.cs:158](/Users/steven/caves-of-ooo/Assets/Scripts/Gameplay/Items/MaterialFieldActions.cs:158)). Finding additional liquid therefore changes contents, but does not yet provide this proposed short-range delivery tool.

**Proposed player situation.** Recover an original pressure-reed applicator from a damaged Sumphold workbench. Fill it with a compatible existing pure liquid. A short directed squirt can prepare a wet electrical target or lay an oil trail across a narrow approach while preserving the flask. It provides no ignition or electrical charge itself; those still need another item, actor or environmental source.

**Bounded implementation.** One repairable tool; one short visible line, one destination, no area cloud; actual stored volume consumed; physical contact routes shared with existing liquid effects. Initially accept only water/oil/brine after verifying each source and dose. An occupied hand, weight and finite fluid distinguish it from carrying disposable preparations. Clotted/frozen/empty contents refuse clearly. A damaged works is a proposed discoverable source, not a claim that this new tool already exists. Existing LiquidFlask availability provides a supply-chain foundation ([LootTables.json:49](/Users/steven/caves-of-ooo/Assets/Resources/Content/Data/Loot/LootTables.json:49)).

**Cost and verification.** Friendly fire and conductivity remain real; walls stop the application; it never manufactures liquid or arbitrary purity. Preserve current mixed-liquid rejection. This is a medium slice because targeting, hostility, repair and feedback need complete integration. Avoid starting a battery ecosystem merely to support this one tool.

## 3. Let preparation answer “when will I need this?”

**Reference choice.** Qud cooking effects hold composed units ([ProceduralCookingEffect.cs:15](/Users/steven/qud-decompiled-project/XRL.World.Effects/ProceduralCookingEffect.cs:15)); triggered variants keep actions separately and describe both trigger and outcome ([ProceduralCookingEffectWithTrigger.cs:12](/Users/steven/qud-decompiled-project/XRL.World.Effects/ProceduralCookingEffectWithTrigger.cs:12), [ProceduralCookingEffectWithTrigger.cs:114](/Users/steven/qud-decompiled-project/XRL.World.Effects/ProceduralCookingEffectWithTrigger.cs:114)). One concrete trigger detects entering the burning state, rather than treating each burning turn as a fresh ignition ([CookingDomainHeat_OnEnflamed.cs:24](/Users/steven/qud-decompiled-project/XRL.World.Effects/CookingDomainHeat_OnEnflamed.cs:24)). This makes preparation interact with subsequent events.

**Actual CoO boundary.** Standard cooking maps an ingredient stack to an authored output ([CookingService.cs:14](/Users/steven/caves-of-ooo/Assets/Scripts/Gameplay/Items/CookingService.cs:14)). Prepared meals currently grant one flat stat bonus from five allowed stats; another meal replaces it ([PreparedMealEffect.cs:17](/Users/steven/caves-of-ooo/Assets/Scripts/Gameplay/Effects/Concrete/PreparedMealEffect.cs:17), [PreparedMealEffect.cs:44](/Users/steven/caves-of-ooo/Assets/Scripts/Gameplay/Effects/Concrete/PreparedMealEffect.cs:44)). Multi-input commissioned food already exists: the kitchen consumes emberwheat and claspbean pulp, with a time/fee tradeoff, for a healing/bleeding field meal ([KitchenBatchPart.cs:108](/Users/steven/caves-of-ooo/Assets/Scripts/Gameplay/World/KitchenBatchPart.cs:108), [KitchenBatchPart.cs:373](/Users/steven/caves-of-ooo/Assets/Scripts/Gameplay/World/KitchenBatchPart.cs:373)). Do not describe all cooking as single-ingredient or all meals as stat buffs.

**Proposed player situation.** Before an expedition, choose ordinary sustained resistance or a binding-grain preparation that spends its one protection charge reducing the next newly inflicted ordinary bleed. The latter frees a future emergency action but is wasted if the expedition never causes bleeding. An ally can receive it through the already implemented sharing route. This is an original design candidate, not an existing recipe or a Qud effect being copied.

**Bounded implementation.** Begin with one conditional recipe using those already edible kitchen inputs, one explicitly named trigger and one saved charge. Retain the one-preparation slot and expiry; make its replacement tradeoff visible. Then add two additional authored recipes only after the first has a meaningful excursion scenario. Reuse food/meal infrastructure; do not build an unrestricted procedural cooking language or duplicate alchemy's property discovery.

**Cost and verification.** Ingredient opportunity cost, meal-slot exclusion and limited duration prevent free stacking. Test trigger versus unrelated status, preexisting versus newly inflicted bleed, actual consumption versus blocked application, charge persistence, simultaneous callbacks and no repeated activation from the same event. Do not broadly rebalance healing or invalidate the existing reactive field meal.

## 4. Defer true mixtures until a destination needs them

Qud persists component identities and uses weighted quantities when combining liquids ([LiquidVolume.cs:1362](/Users/steven/qud-decompiled-project/XRL.World.Parts/LiquidVolume.cs:1362), [LiquidVolume.cs:1411](/Users/steven/qud-decompiled-project/XRL.World.Parts/LiquidVolume.cs:1411)); even cleansing depends on mixture composition ([LiquidVolume.cs:5438](/Users/steven/qud-decompiled-project/XRL.World.Parts/LiquidVolume.cs:5438)). CoO instead has scalar vessel contents and deliberately refuses mixed sources/destinations to avoid generating pure resources from contaminated cells ([LiquidVesselService.cs:241](/Users/steven/caves-of-ooo/Assets/Scripts/Gameplay/Items/LiquidVesselService.cs:241), [LiquidVesselService.cs:273](/Users/steven/caves-of-ooo/Assets/Scripts/Gameplay/Items/LiquidVesselService.cs:273)).

This is a real architectural difference, but not a defect to remove casually. A future Sodden reclamation site could justify it: carry contaminated feedstock, spend filters/heat recovering a smaller useful fraction, or transport the unsafe mixture for an intentional hazard. Dilution must not mean deletion of the dangerous component. Require that authored play loop before undertaking a component model, conversion policy for existing saves, consistent coat/pool/container sampling and conservation tests. Keep this fourth in the roadmap; the first three do not require it.

## Review and limits

- 🔵 Scope correction: the reference sprayer applies to carried/equipped objects; the proposed short-range world tool is CoO-original design, not claimed parity.
- ⚪ Deliberate limit: no general cosmetic staining, universal solvent, mixture rewrite, arbitrary meal language or energy-cell framework proposed for the first slice.
- 🧪 These are source-grounded design recommendations. This investigation ran no new tests, no Qud runtime session and no visual review; implementation must follow the repository's failing-test, counter-check and live-scenario gates.
